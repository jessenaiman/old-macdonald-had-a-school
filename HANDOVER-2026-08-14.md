## Product intent that must not be lost

- This is a small teacher-resource website with roughly five important page families, not an enterprise dashboard.
- The visual language is an Old MacDonald farm-school teaching system: useful classroom notes, sewn patches, fabric, pins, character portraits, curriculum icons, and warm educational playfulness.
- Visual choices must explain educational purpose. Portrait identifies who is present; character color identifies ownership; fabric communicates construction; icon communicates the learning action or subject; grade/subject relationships explain curriculum context.
- The home page should become the working visual reference for the rest of the site.
- The grade workspace must remain full width. Do not impose a root `max-width` or global horizontal page margin.
- Character colors must be semantic global theme tokens, never duplicated as color names or hex values in page copy/components. Changing one character token should propagate everywhere that identity is used.
- Asset URLs belong only in `app/brand-assets.css`; components consume semantic asset classes/names.
- Use the existing database, Drizzle, SQLite, and semantic-search work. Files in `lib/` can support page rendering and routing but are not automatically database records.

## Confirmed failures and unfinished work

### 1. The site is not visually unified

Home, About, Songs, Search, lessons, topics, branding, and grade workspaces currently use inconsistent widths, surfaces, typography, and component recipes. Do not solve this by constraining every route in the root layout. Establish a small set of documented page patterns while preserving route needs:

- Full-width workspace: grades and other true work areas.
- Branded landing/reference: home and branding.
- Readable teaching document: lessons, songs, and topics.

All three must visibly share navigation, semantic theme tokens, typography, materials, Card recipes, spacing rhythm, and responsive behavior.

A final read-only wrapper audit found these concrete competing width systems:

- Home and the five grade hubs are full width with local section/panel gutters.
- Header and footer use an inner `max-w-screen-2xl` container, so they can appear narrower than full-width content on very wide screens.
- Branding uses `max-w-screen-2xl` plus its own responsive gutters.
- Grade lesson details use `w-[calc(100%-1rem)] max-w-7xl overflow-hidden`; the overflow rule can clip pins and patch edges.
- Search is full width but owns another `px-3 sm:px-6 lg:px-10` gutter system.
- Topics and Lessons use separate `min(...)`/`calc(...)` viewport-width formulas.
- Topic details use a full-page surface plus a separate `max-w-5xl` article.
- Songs combines viewport-calculated padding with `max-w-6xl`, constraining the route twice.
- About adds `max-w-screen-xl` and overrides the root material with `bg-background`.
- The generic lesson detail has no page-owned surface or padding and depends on root/internal styles.

Converge by removing arbitrary route-level viewport arithmetic and keeping width constraints only on genuinely readable inner content. This is not permission to make every route literally the same width.

### 3. shadcn rules were not followed consistently

Audit all recently changed UI before accepting it. Known violations or risks include:

- Raw checkbox markup on the Songs search/filter page. Add/use the actual shadcn Checkbox only after reading its CLI docs and reviewing the dry run.
- Custom separators implemented with border-only divs/list items instead of `Separator` where the rule applies.
- Custom styled spans where `Badge` should be used.
- `className` overriding component colors/typography instead of using semantic variants/tokens.
- Custom Card-like surfaces that may not use full `CardHeader`, `CardTitle`, `CardDescription`, `CardContent`, and `CardFooter` composition.
- Component work performed without first running `npx shadcn@latest docs <component>` and fetching the returned documentation.

The local shadcn CLI was slow and one `info --json` attempt timed out. Do not use that as permission to guess APIs or hand-roll replacements. Diagnose the CLI or use the already installed component source and official docs.
