# Hindsight mental-model refresh failures

**Research date:** 2026-09-13  
**Scope:** Hindsight CLI behavior, mental-model refresh scheduling/execution, async-operation states, WSL/Windows implications, and plausible causes for the dashboard pattern supplied with this task.

## Executive findings

- A mental-model refresh is not a local synthesis performed by the CLI. The CLI submits `POST /v1/default/banks/{bank_id}/mental-models/{mental_model_id}/refresh`; Hindsight queues a background `refresh_mental_model` operation that re-runs the model's `source_query` through Reflect and updates the model asynchronously. The CLI prints the returned operation ID and tells the operator to inspect the operation status. [CLI command definition](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-cli/src/main.rs#L1117-L1137), [CLI implementation](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-cli/src/commands/mental_model.rs#L475-L515), [API route](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/api/http.py#L6523-L6555), [official mental-model API docs](https://hindsight.vectorize.io/developer/api/mental-models#refresh-a-mental-model).
- `deferred` in the dashboard should be read as a pending operation deliberately parked for later, not as a terminal failure. Upstream represents this as `status=pending` plus a future `next_retry_at`; the field is used for refreshes held by `min_refresh_interval_seconds` and for extension/backpressure deferral. Deferral does not increment `retry_count` or write an error message. [Operation response model](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/api/http.py#L4213-L4229), [defer exception](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/worker/exceptions.py#L25-L43), [poller handling](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/worker/poller.py#L1217-L1222).
- `processing` means a worker has claimed the operation. A processing row that never advances can be a worker/zombie problem, especially after a restart with an unstable worker identity; upstream documents `hindsight-admin worker-status` and worker decommission commands for recovery. [Admin CLI recovery docs](https://hindsight.vectorize.io/developer/admin-cli#recovering-stuck-or-zombie-operations).
- `failed` is terminal for that attempt. The dashboard's supplied **328 failed** entries cannot be attributed to one root cause from counts alone: the decisive evidence is each operation's `error_message`, `retry_count`, `operation_type`, `created_at`/`updated_at`, and (for finished refreshes) typed result details. The API explicitly supports filtering operations by `status=failed` and `type=refresh_mental_model`. [List operations route](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/api/http.py#L7614-L7660), [get-operation route](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/api/http.py#L7662-L7689).

## How refresh is invoked

Hindsight describes mental models as saved Reflect responses. Creating one runs Reflect using its `source_query` and stores the result; future Reflect calls can consult the precomputed summary. Manual refresh is the documented CLI command:

```bash
hindsight mental-model refresh "$BANK_ID" "$MENTAL_MODEL_ID"
```

The command submits work and returns an operation ID; it does not wait for the synthesis to finish. The same endpoint is used by the control plane and SDKs. The current upstream handler returns `status="queued"` at submission time, while the worker later moves the operation through pending/processing to a terminal result. [Mental-model concepts/API](https://hindsight.vectorize.io/developer/api/mental-models), [official CLI docs](https://hindsight.vectorize.io/sdks/cli#mental-models), [Rust CLI source](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-cli/src/commands/mental_model.rs#L475-L515), [API source](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/api/http.py#L6523-L6555).

For diagnosis, upstream also exposes a dry-run refresh endpoint/CLI command. It runs the production refresh pipeline, including the same LLM work, but skips persistence of content and watermark and returns the resolved mode, scope/window, retrieval counts, candidate content, diff, warnings, and trace. It is therefore the most targeted non-destructive reproduction once the bank/model IDs and API endpoint are known. [Dry-run API description](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/api/http.py#L6557-L6575), [CLI dry-run source](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-cli/src/commands/mental_model.rs#L517-L547).

## Automatic refresh and the dashboard's deferred row

A model can refresh automatically after consolidation or on a cron schedule. The minimum automatic-refresh interval is hierarchical: server, bank, or model. When a trigger fires inside the interval, Hindsight queues one refresh and parks it until the window closes; subsequent triggers fold into that queued refresh rather than creating unbounded duplicate work. Explicit API/MCP/control-plane refreshes ignore that floor and release a parked refresh they fold into. `0` disables the floor. [Configuration reference](https://hindsight.vectorize.io/developer/configuration#mental-models), [upstream implementation/feature discussion](https://github.com/vectorize-io/hindsight/pull/3621).

The supplied `deferred` item is therefore consistent with normal backpressure/rate-window behavior if it has a future `next_retry_at`. It is not evidence that the LLM failed. If it remains pending past its scheduled time, inspect the operation record and worker logs; a worker outage, disabled worker, or database connectivity problem becomes more likely.

Upstream also fixed a scheduling class where server-default models were initially refreshed against empty newly-created banks. The fix defers those initial auto-refreshes until consolidation, avoiding LLM work that cannot produce content and avoiding head-of-line blocking of the bank's seed retains. This matters if many failed rows were created immediately after bank initialization. [Issue #3875](https://github.com/vectorize-io/hindsight/issues/3875), [fix PR #3905](https://github.com/vectorize-io/hindsight/pull/3905).

## What `failed` can mean

The refresh implementation documents and records several distinct failure paths:

1. **Reflect retrieval/tool failure.** A retrieval tool can raise before a candidate answer exists; upstream classifies this as `retrieval_failed`, preserves the previous content and watermark, and re-raises a refresh error so the operation is visibly failed. [Refresh implementation](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/engine/memory_engine.py#L17018-L17090).
2. **No answer from the Reflect agent.** A no-answer result is classified as `no_answer`; previous content remains intact and the failure is recorded. [Same implementation](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/engine/memory_engine.py#L17064-L17090).
3. **Unsafe/empty/invalid synthesis or structured-output failure.** The implementation's failure contract includes empty output, delta operations that do not yield a document, structured-output extraction failure, and Reflect failure before a candidate exists. The failure path writes audit metadata but deliberately does not advance content or the memory watermark, so retrying reads the same window. [Refresh failure contract](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/engine/memory_engine.py#L17045-L17053), [preserve-and-fail path](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/engine/memory_engine.py#L17146-L17173).
4. **LLM/provider problems.** Refresh uses Reflect and internal recall, so invalid/missing provider configuration, authentication/quota errors, provider HTTP errors, unsupported structured-output settings, context-length errors, and provider latency can fail the worker task. Upstream's configuration documents Reflect's `300`-second wall timeout, a `100000`-token default accumulated context ceiling, and separate internal-recall token budgets. [Reflect/internal-recall configuration](https://hindsight.vectorize.io/developer/configuration#reflect).
5. **Worker/runtime/database failures.** The worker marks unhandled exceptions failed; if even the failure-marking database write fails, the row can remain `processing` until reconciliation. A permanently processing row after worker loss is the documented zombie case. [Poller exception path](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/worker/poller.py#L1223-L1259), [zombie recovery docs](https://hindsight.vectorize.io/developer/admin-cli#recovering-stuck-or-zombie-operations).

A historical first-party issue is especially relevant if the instance uses the `claude-code` provider: Hindsight 0.8.5 had a Reflect bug in which the agent made zero tool calls and returned a “no information” answer, causing mental-model refreshes to fail or overwrite useful content; the issue was closed by PR #2980. Treat this as version/provider-specific evidence, not a diagnosis of the current instance. [Issue #2966](https://github.com/vectorize-io/hindsight/issues/2966), [closing PR #2980](https://github.com/vectorize-io/hindsight/pull/2980).

## WSL-only CLI: what upstream actually says

The current official installation guide lists Windows x86_64 as fully supported for Docker, bare-metal pip, and the embedded database. The repository README still presents the CLI installer as `curl -fsSL https://hindsight.vectorize.io/get-cli | bash`, which is naturally a POSIX-shell command and commonly leads Windows users to run it under WSL. [Installation platform matrix](https://hindsight.vectorize.io/developer/installation#supported-platforms), [repository quick start](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/README.md#quick-start).

That does **not** establish that the Hindsight API or current CLI protocol is inherently WSL-only. Upstream shipped explicit Windows native CLI support in commit `4ba54d8c8fb826138c41ad13bd214063643f6d5d`: it built/staged a Windows Rust CLI executable, taught embedded discovery to look for `hindsight.exe`, and removed the Unix-only executable-bit check on Windows. [Official commit](https://github.com/vectorize-io/hindsight/commit/4ba54d8c8fb826138c41ad13bd214063643f6d5d), [Windows-aware binary discovery source](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-embed/hindsight_embed/daemon_client.py#L45-L85).

Therefore, “the CLI only works in WSL” is most likely an installation/distribution/version/environment constraint in this deployment—e.g. the installed release has only a Linux binary, the POSIX installer is being used from Windows, or PATH/API URL/auth differs between Windows and WSL—not a mental-model refresh semantic requirement. Running the CLI in WSL can still be a valid workaround, but it should target the same Hindsight API and bank as the dashboard.

## Evidence-led next checks

1. From WSL (the known-working shell), list only refresh failures and capture the exact fields; do not infer a cause from the 90% count:

   ```bash
   hindsight operation list "$BANK_ID" --output json
   # Or query the API directly:
   curl -s "$HINDSIGHT_API_URL/v1/default/banks/$BANK_ID/operations?type=refresh_mental_model&status=failed&limit=100"
   ```

   The CLI's documented operation commands are [here](https://hindsight.vectorize.io/sdks/cli#operation-management); the API's supported status/type filters are [here](https://github.com/vectorize-io/hindsight/blob/bde55237f53bf55aacd048b01e29d7dc23b83a85/hindsight-api-slim/hindsight_api/api/http.py#L7623-L7634).

2. Pick one recent failed operation and call `operation get` (or `GET .../operations/{operation_id}`); record `error_message`, `retry_count`, `next_retry_at`, and typed result details. A missing/blank error message is itself useful evidence of an older operation or a failure while recording failure metadata.
3. Pick one affected mental model and run the non-destructive dry run. Check `warnings`, `outcome`, `mode_fallback_reason`, `facts`, `based_on`, and `trace`; this separates empty scope/no answer/retrieval failure from provider/schema/timeout issues without changing the model.
4. Check model trigger settings and bank contents. If the bank was empty when defaults were created, upgrade to a release containing the empty-bank scheduling fix or disable automatic refresh until the bank has consolidated memories; then manually refresh once.
5. Verify the Hindsight server's configured Reflect provider/model/API credentials and logs, not only the Hermes client. Hermes's native provider performs automatic recall before turns and asynchronous retain after responses; mental-model refresh is a Hindsight-side background Reflect operation and is not proof that ordinary Hermes recall/retain is healthy. [Official Hermes integration](https://hindsight.vectorize.io/sdks/integrations/hermes).

## Bottom line for the supplied dashboard

The counts show a severe refresh-operation failure/backlog pattern, but not its root cause. The deferred and processing rows are non-terminal states; the 328 failed rows require their stored error messages to classify. The strongest upstream-supported hypotheses are (a) provider/Reflect failures repeated by automatic triggers, (b) refreshes created against an empty bank on an affected older release, (c) a version-specific Reflect/provider incompatibility, or (d) worker/database/runtime failures. The next reliable action is to extract one failed operation's `error_message` and run a dry-run refresh against the same bank/model; WSL is only the shell used to reach the CLI in this setup, not evidence that refresh itself is WSL-dependent.
