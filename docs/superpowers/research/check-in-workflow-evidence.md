# Evidence for a safer check-in workflow

## Proposed project policy

For this repository, use one short-lived branch per coding task, keep commits and the resulting pull request focused, run the repository's local gates, and merge through a pull request rather than committing directly to `main`.

This policy is a **project choice informed by the evidence below**. The sources strongly support short feedback cycles, small coherent changes, review, automated tests, and protection of the mainline. They do **not** establish that every task in every team must map one-to-one to a branch, nor that pull requests are always superior to direct-to-trunk development.

## What primary sources strongly support

- **A lightweight branch-to-PR workflow is GitHub's documented default.** [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) is explicitly branch-based: create a separate branch for each set of unrelated changes, make and commit changes, open a pull request, address review, merge, then delete the branch. GitHub's [pull-request reference](https://docs.github.com/en/pull-requests/reference/pull-requests) describes PRs as proposals that gather discussion, review, diffs, checks, and merge requirements so teams can catch issues before merging; its [review guidance](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes) says small, focused PRs are easier to review and safer to merge.
- **Small, self-contained changes materially improve review and recovery.** Google's [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html) recommends one self-contained change that addresses one thing and includes related tests. It says small changes are reviewed faster and more thoroughly, are easier to reason about, merge, and roll back, and are less likely to introduce bugs. It also recommends separating substantial refactoring from feature or bug-fix changes. Google's [CL description guidance](https://google.github.io/eng-practices/review/developer/cl-descriptions.html) requires a focused summary plus the what and why, preserving useful change history.
- **Short-lived integration and small batches are associated with delivery performance.** DORA's [trunk-based development guidance](https://dora.dev/capabilities/trunk-based-development/) reports higher software-delivery and operational performance for teams with three or fewer active branches, at least daily merges to trunk, and no integration phases or code freezes. Its [small-batch guidance](https://dora.dev/capabilities/working-in-small-batches/) says small batches shorten feedback and remediation time and recommends independently testable work completed in hours to a couple of days.
- **Tests before integration are essential, not optional ceremony.** DORA calls not running automated tests before commit a trunk-based-development pitfall and recommends meaningful automated tests before every commit, a fast build, and immediate repair or reversion when trunk turns red ([trunk-based development](https://dora.dev/capabilities/trunk-based-development/)). Google's small-CL guidance says related tests belong in the same change and each submitted change must leave the system working ([Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)).
- **Policy should be enforced at `main`, not left to memory.** GitHub documents branch protection and rulesets that can require a pull request, approvals, resolved conversations, and passing status checks, while restricting pushes, force-pushes, deletion, and bypasses ([protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [rules available in rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). Required checks make the shared, reproducible gate authoritative even when local checks were run.

## Nuance and counterevidence

- **A PR for every task is not a universal research conclusion.** DORA defines trunk-based development as integrating small batches at least daily and explicitly discusses developers pushing directly to trunk. The authoritative practitioner guide [Committing straight to the trunk](https://trunkbaseddevelopment.com/committing-straight-to-the-trunk/) presents direct commits as viable for small, closely coordinated teams with a fast, exhaustive build and rapid revert discipline. Thus, "never direct to `main`" is a reasonable governance choice for this repository, not a universal requirement.
- **Short-lived means genuinely short-lived.** DORA contrasts branches lasting hours with feature branches lasting days or weeks. The practitioner guide on [short-lived feature branches](https://trunkbaseddevelopment.com/short-lived-feature-branches/) recommends roughly a couple of days at most, one developer (or a pair), prompt merge, and deletion. A branch-per-task policy that produces week-long branches would work against the evidence.
- **Review can become a bottleneck.** DORA warns that heavyweight or slow asynchronous review causes developers to batch work, delays integration, and increases conflict risk. It recommends synchronous review or making review a team priority ([trunk-based development](https://dora.dev/capabilities/trunk-based-development/)). Google's [code-review standard](https://google.github.io/eng-practices/review/reviewer/standard.html) likewise favors approval once a change definitely improves code health rather than delaying for perfection.
- **"Focused commits" needs careful interpretation.** The strongest evidence concerns the reviewable change/CL (roughly the PR), not a mandate that every intermediate commit be independently reviewed. Commit history should remain intelligible, but safeguards should evaluate the final proposed merge. Large generated changes and trusted automated refactors can also justify exceptions, with explicit reviewer agreement and extra testing ([Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)).
- **Local gates are necessary but insufficient.** A local run can become stale as `main` changes and can differ by environment. Keep local gates for fast feedback, but require equivalent CI checks on the proposed merge. GitHub notes that PR checks and merge status expose automated validations and blockers ([pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)).

## Recommended safeguards for this repository

These are **project-specific implementation decisions**, derived from—not dictated verbatim by—the sources:

1. Protect `main` with a GitHub ruleset: require PRs **and separately configure** at least one approval where another reviewer is available, resolved conversations, and required CI checks; block force-pushes and deletion; avoid routine administrator bypass. Requiring a PR alone does not require approval ([ruleset rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
2. Make CI rerun the same documented gates as local development. Pin required checks to their expected GitHub App where possible, because GitHub warns that otherwise a user with write access can set a status; ensure workflows do not turn a skipped required job into an unintended successful check ([status checks](https://docs.github.com/en/pull-requests/reference/status-checks)). Require checks against an up-to-date base or use a merge queue when concurrency makes stale approvals/checks risky.
3. Keep branches under one working day when practical and no more than a couple of days normally; merge at least daily. Delete them after merge. If a task cannot fit, split it across multiple independently safe branches/PRs rather than equating one task with one large PR; use feature flags or branch-by-abstraction for incomplete user-facing work.
4. Define “focused” at the PR level: one coherent purpose, related tests included, meaningful description of what and why, and no unrelated refactor. Prefer a small sequence of understandable commits; squash on merge when intermediate commits are merely work-in-progress.
5. Keep review lightweight and prompt. Use draft PRs for early visibility, identify code owners only for genuinely sensitive areas, and do not demand perfection when the change improves code health and passes policy.
6. Establish a visible break-glass path for emergencies: narrowly authorized bypass, recorded reason, immediate follow-up review, and prompt revert or fix if `main` is red. Monitor branch age, PR lead time, check duration/failure rate, and time-to-green so the controls do not create larger batches.

## Bottom line

Adopt the proposed policy as a strong default because it combines GitHub's native review model with Google's small-change guidance and DORA's emphasis on small batches, fast tests, and frequent integration. Its success depends less on the mere existence of branches and PRs than on keeping them small and short-lived, automating enforcement on `main`, making review fast, and retaining a controlled emergency path.
